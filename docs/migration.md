# Migrating hal_agent to another machine

The goal: a fresh `git clone` on a new server is small, and a few scripted steps
get you to "run and test exactly like before." The repo deliberately tracks **only
code, configs, prompts, curated test sets, and manifests** — no datasheets, no
generated/LLM output, no databases. Everything else is either restored from a
GitHub Release (device assets) or regenerated locally (vector DB).

## What does and doesn't travel with a clone

| Travels with the clone | Restored / regenerated on the new machine |
|---|---|
| All source, prompts, configs | `devices/**/*.pdf`, `*.svd` → from the GitHub release (`unpack_device_assets.py`) |
| `devices/**/*.md`, `keyword_infos.json` | `databases/` (local ChromaDB) → regenerated by preprocessing |
| `ASSETS_MANIFEST.tsv`, `verified_datasheet/` | `chunked_datasheets/` → regenerated by preprocessing |
| Curated test sets (`optimization_validator/.../test_set_*.csv`) | `agent_output/`, `evaluation/` → produced by running the pipeline |
| `requirements.txt`, `Dockerfile`, scripts | experiment/LLM outputs (kept only on the machine that produced them) |

Generated artifacts (`agent_output/`, `evaluation/`, `databases/`,
`chunked_datasheets/`) and experiment-run trees are gitignored, so they never
re-enter git. See `docs/device_assets.md` for the device-asset packing details.

## One-time, on the current machine

Publish the device assets to a GitHub release so a new machine can pull them:

```bash
source .venv/bin/activate
python scripts/pack_device_assets.py --upload --tag device-assets   # builds dist/ archives + uploads
git push                                                            # ASSETS_MANIFEST.tsv is committed
```

## On the new machine

Prerequisites: **docker**, **gh** (run `gh auth login`), **python3**.

```bash
git clone https://github.com/Ramla-I/hal_agent.git
cd hal_agent

cp .env.example .env          # then fill in OPENAI_API_KEY / GROQ_API_KEY
scripts/bootstrap.sh          # restore assets -> build image -> regenerate the rm0041 vector DB
```

`bootstrap.sh` runs three steps: `unpack_device_assets.py` (downloads + verifies the
PDFs/SVDs), builds the Docker image, then regenerates the local vector DB for the
default device (`rm0041`) from its PDF. Pass `--skip-preprocess` to stop after the
image build, or a device name to target a different one.

## Running things (in Docker)

Long jobs run in the container; **the whole repo is bind-mounted at `/app`, so you
edit code on the host and outputs land on the host** — same loop as local dev.

```bash
scripts/docker_run.sh s0 --devices rm0041                      # full pipeline (long-running)
scripts/docker_run.sh s0 --devices rm0041 --coverage-improver-iterations 0 --skip-validator  # quick smoke run
scripts/docker_run.sh preprocess devices/stm/rm0041/rm0041.pdf rm0041   # (re)build a device's vector DB
scripts/docker_run.sh shell                                    # interactive shell for testing
scripts/docker_run.sh run scripts/calculate_generator_coverage.py       # any python entrypoint
```

API keys come from `.env` (`--env-file`). Downloaded embedding/reranker models are
cached under `.docker_cache/` so they aren't re-fetched every run.

### Without Docker

The classic flow still works if you'd rather use a venv:

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python scripts/unpack_device_assets.py --tag device-assets
python context_retrieval/preprocessing/pipeline.py devices/stm/rm0041/rm0041.pdf rm0041 \
    --format markdown --embed-metadata --backend local
python core/s0_run_full_analysis.py --devices rm0041
```

## Verifying a clone is healthy

```bash
python scripts/unpack_device_assets.py --verify-only   # all assets present + sha256 match
scripts/docker_run.sh s0 --devices rm0041 --coverage-improver-iterations 0 --skip-validator
```
