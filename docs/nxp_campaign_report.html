NXP Full-Sweep Campaign

All NXP devices run end-to-end, discovered, fixes shipped. Includes a mid-campaign correction to the measurement that overturned the original priority list.

Bottom line. Running every NXP format family end-to-end, with a corrected measurement, shows the extraction is in much better shape than first thought: the generator already finds 94–100% of registers and extracts offsets itself across all four families — no per-family adapter or parser needed. A set of pipeline fixes unblocked 949 confirmed access-constraints across the 8 devices (NXP emitted almost none before), and throughput fixes made the giant parts finish at all. The one real structural weakness is reset-value extraction (23–55% everywhere); array reconciliation (built this round) closed most of the small register-coverage gap.
⚠ Measurement correction (important). The first version of this report said register coverage was 60–92% and ~1,721 registers were "absent," making array reconciliation look like the top lever. That was a join bug in the discovery tool: it keyed SVD cluster/array registers differently than the generator names its files (FTFE_FlashConfig_BACKKEY0 vs ftfe_flashconfig_backkey0), so it counted ~1,130 produced registers as missing. Fixed to measure against the generator's own enumeration (commit device_discovery fix). Corrected: register coverage 94–100%, true absent 591 (3%). The numbers below are the corrected ones.

The real finding: offsets are already solved; the plan changed

We began with a per-family plan (a Group B absolute→offset adapter "covering 5 devices," a Group D caption parser) and, after the first measurement, thought array reconciliation was the top lever. All three were wrong once measured correctly. The generator extracts offsets itself in every family (Group C 92%, B 76–91%, A 51–63%, D 45–48%), finds 94–100% of registers, and the adapters/parser are unnecessary. Array reconciliation is real but small (recovers ~243 of 18k registers). Per-device discovery — and fixing the discovery's own join bug — is what kept us from building the wrong things.

Recommended next work (prioritized, corrected)

1. Reset-value extraction — the one real universal gap

Reset is 23–55% on every device (worst on classic Kinetis: k64 23%, mk20d7 28%). It's the lowest-coverage field everywhere and affects all registers. Needs a principled per-bit reset assembler (assemble the register reset from the per-bit "Reset value" column; the blind zero-default was rejected earlier, +82 wrong). Biggest remaining lever.

2. Group D offsets + size

lpc55s69 / mimxrt685s caption-style offsets are only ~47% and size 24–47% — the one place the generator clearly underperforms on structure. Worth investigating the retrieval/prompt for caption-style register sections (a caption-aware pass, now that the data shows it's warranted).

3. Scatter recovery (batch-failure resume)

Of the 348 still-absent, ~311 are sibling-less: one-off batch failures (quadspi_mcr, usb0_*, systick_*) and whole-missed arrays (flash_key_store_activation_code*). A targeted resume/retry of the failed batches (not array cloning) would recover the one-offs.

4. read_effect consequence + below-gate rejects

Generator emits read_effect without the required consequence → invalid_v2_constraint rejects. Small prompt/schema fix, recovers constraints on every device.

Per-group verdicts (corrected)

  • Group A (k32l3a, s32k1xx): constraint-rich (176, 200); address moderate (51–63%); array reconciliation + reset the gaps.
  • Group B (ke04, k64, mk20d7): best offset/size (76–91%), very constraint-rich (43, 210, 211); worst reset (23–28% on the big ones). No adapter needed.
  • Group C (lpc845): the one device the summary-fill helps (85→93% address); strong offsets.
  • Group D (lpc55s69, mimxrt685s): generator reads caption offsets but only to ~47%, size ~35% — the weakest structural group; caption-aware retrieval worth trying. No parser retraction needed after all; it under-reads, it doesn't fail.
