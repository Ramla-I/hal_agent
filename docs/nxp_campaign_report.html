NXP Full-Sweep Campaign

All 8 NXP devices run end-to-end, discovered, and the per-device findings compiled. What we fixed, what the generator already does well, and what to build next.

Bottom line. Running every NXP format family end-to-end overturned the plan we started with. We assumed each family would need its own structural adapter; in fact the generator already extracts register offsets on its own across all four families (57–92%) — no per-family fill or parser required. The real wins were elsewhere: a set of pipeline fixes unblocked 949 confirmed access-constraints across the 8 devices (NXP was emitting almost none before), and throughput fixes made the giant parts finish at all. The remaining gaps are universal, not per-family: array/dim register reconciliation and reset-value extraction.

The big surprise: offsets are already solved

We began with a per-family plan: a Group B absolute→offset adapter (flagged "highest ROI, covers 5 devices") and a Group D caption parser. Both are retracted. The empirical runs show the generator extracts offsets on its own in every family — Group B 57–90%, Group D 60–72%, Group A 60–70%, Group C 92% — with no adapter and no parser. The cross-chunk summary-fill, which we built for lpc845, is a confirmed no-op on Groups A and B (it fills 0; the generator already has the values) and doesn't apply to D. So the only structural extractor that earned its keep is the Group-C summary-fill, and even that is marginal. This is exactly why per-device discovery was worth it — the a-priori adapter plan would have been wasted effort.

Recommended next work (prioritized)

All universal (cross-group / cross-vendor), none built yet. ASK = significant change, I'll confirm with you before implementing.

1. Array / dim register reconciliation ASK

The single dominant gap on every device. SVDs expand register arrays to concrete names (DMA_TCD0..15_*, MPU_RGDn_WORDm, FTF*_BACKKEY0..7, IOPCTL_PIO0_*) but the datasheet documents them once generically, so the generator leaves them absent. 1,721 absent registers total (s32k1xx 637, lpc55s69 439, mimxrt685s 227, k64 233, mk20d7 100…) plus hundreds of array-indexed missing offsets, plus the unresolvable_in_svd constraint rejects (18–71/device). One reconciliation (compute per-instance base + n×stride; map SVD array names ↔ the generic documented name) recovers registers and constraints at once. Biggest lever by far.

2. Reset-value extraction ASK

The weak axis everywhere — 21–60%, worst on classic Kinetis (k64 21%, mk20d7 26%). Reset values live in a per-bit table column the generator doesn't reliably assemble. Needs a principled per-bit reset assembler (the blind zero-default was rejected earlier: +82 wrong). Would lift every device.

3. Retry-overwrite merge ASK

The empty-field retry re-generates field-less registers with force=True and overwrites the whole file — so a register can lose an address_offset it already had (k32l3a dropped ~80%→60% address this way). The retry should merge recovered subfields into the existing record, not clobber structural fields. Cross-vendor; would also help STM.

4. read_effect consequence + below-gate constraint rejects

The generator emits read_effect constraints without the required consequence field → invalid_v2_constraint rejects (a chunk of the 14–53 rejects/device). A small prompt/schema fix. Low-risk, no need to ask.

Per-group verdicts

  • Group A (k32l3a, s32k1xx): constraint-rich (176, 200); summary-fill is a no-op; array reconciliation dominates (s32k1xx 637 absent).
  • Group B (ke04, k64, mk20d7): generator handles offsets 57–90% with no adapter; very constraint-rich (43, 210, 211); reset is the worst here (21–26% on the big ones).
  • Group C (lpc845): the one device the summary-fill helps (85→93% address); reference device.
  • Group D (lpc55s69, mimxrt685s): generator reads caption offsets directly (60–72%); caption parser unnecessary; big array/config-page blocks absent.
