Where our datasheet rules would bite — and where the compiler agrees

22 open-source embedded projects read against constraints extracted from their chips' reference manuals. The survey is static — each project's own Rust source is parsed for register accesses and cross-referenced — and where a project could be brought to the PAC generation we inject, it was then compiled against the injected crate: 5 projects measured that way (anne-key, blackpill-usb-pwdstore, elodin-sensor-fw, hubris, stm32-eth), 1 attempt recorded as blocked, and the scan's blind spot (writes that leave the typed API) is bounded at the bottom of the page.

Purpose

Datasheets attach preconditions to register writes ("SWSTART may be set only when ADON = 1"). This project extracts those rules from ST reference manuals and injects them into the generated chip crates as compile-time gates. The question this page answers: where would those rules bite in real, third-party code?

Two evidence grades, kept separate throughout. Compiled (next section): the project was built against an injected crate and every listed site is a compiler diagnostic. Scanned (the section after): the project’s own source was read statically and cross-referenced against the constraints — the reach is wider, the claim weaker. Driver-level compile results across the whole 49-manual corpus live on the companion register-constraints tracking page, not here. Nothing on this page is a confirmed bug: gates prove an access is real, triage says whether a check is visible nearby, and the human verdict lives in the review ledger.

Ported and actually run — what the compiler found

Each project below was built against an injected crate: constraints in, whole dependency graph compiled, every listed site a real diagnostic. This is the stronger evidence grade on this page; the scan (next section) covers everything a build cannot yet reach.

Read the verdicts with this in mind: a confirmed TRUE NEGATIVE: the scan reported 0 hits and the compiler agrees. RM0386 constrains ADC1, CAN1, CRYP, DSI, I2C1, IWDG, QUADSPI, RNG, SPI1 and USART1; stm32-eth touches ETH_MAC, ETH_DMA and ETH_PTP, so there is no overlap to fire on. Two access paths in this driver would evade the gate if a constrained register ever went through them: bit banding, which writes via a raw pointer and so never calls Reg::write, and the DelayedReg<T> wrapper, which would fail to compile in one generic body rather than at the call site. Neither costs a finding here.

stm32f7-discovery

Board framework with its own SD, Ethernet and LCD drivers; 261 register accesses, the densest project scanned.

attempted — blocked  the scan called this pac-gap (the recorded pin (0.7) disagrees with the manifest (0.3.2); the manifest wins; pins stm32f7 0.3.2, injector targets 0.16.0). A build attempt says otherwise: No toolchain builds both. The PAC generation the injector targets needs Rust 1.65 and edition 2021, so it cannot be compiled on the 2019 nightly the project pins; and the project's dependency stack -- cortex-m 0.1.8, linked_list_allocator 0.6.4, spin 0.4.10, plus a local crate named `core` -- does not compile on a current one. None of the errors is in the project's own source: its register code never gets compiled at all, so the PAC bump is not what blocks it and porting 0.3.2 to 0.16 would not help. Reaching these 4 sites means first moving the application off 2019 Rust, which is a rewrite of the project rather than a port of a dependency.

Evidence. cargo check on nightly-2025-06-23 with the toolchain pin removed: 40 errors, 0 of them in the project's own source. By crate: cortex-m-0.1.8 26, core 4, linked_list_allocator-0.6.4 3, spin-0.4.10 1. It pins nightly-2019-04-26; the PAC needs Rust 1.65 / edition 2021.

the scan's 4 sites stand as static claims: i2c.rs:468 (OAR2, unchecked), init/mod.rs:49 (PLLCFGR, corroborated), init/mod.rs:66 and :69 (PWR_CR1, unchecked and corroborated). Note :66 writes ODEN while the gated field is ODSWEN, so field gating would likely not fire there -- the same register-vs-field granularity gap anne-key showed, but unverified here.

What this cannot see

A static scan sees no runtime guards, so unchecked means candidate, not bug; compile confirmation is the eventual arbiter. Peripheral attribution is heuristic — it comes from the receiver expression, falling back to the module the code lives in. Chip attribution is per path prefix and derived from each driver crate's own build features, not the family in its name; getting that wrong is not conservative, and an earlier run matched Hubris's shared I²C driver against an F4 manual whose I²C is a different peripheral generation, manufacturing 14 findings. Whole-register gates over-approximate: when a rule lists no restricted fields it gates the whole register, though the datasheet note usually attaches to specific bits — read the fields written column before the verdict.

Register writes that leave the typed API entirely

Every compile-confirmed number on this page is a lower bound, and this measures the gap. Enforcement is a trait bound on the register type’s access methods; bit banding writes a register through a raw pointer (bb::set(rcc.bdcr(), 0) — ARM maps each peripheral bit to its own word address), so the write never calls a gated method and compiles whatever markers the register carries. experiments/bitband_scan.py finds these calls, resolves the bit number to a field through the PAC’s own generated accessors, and cross-references the constraints. Across 14 (driver, manual) pairings — every locally available sweep consumer that uses bit banding — it finds 16 writes to constrained fields that no gate can see. “Zero hits” on this page means “nothing went through the gated API”, not “nothing touched the register”.
