Datasheet Format Families

How NXP and STM reference manuals present register structure — and why it shapes our extraction pipeline.

The headline. The two vendors sit at opposite ends of a spectrum. STM is one uniform family — all 53 reference manuals we process, spanning ~15 years (STM32F1 → STM32U5), use the same house style. NXP splits into four distinct families, a legacy of the mergers that formed the company (Freescale's Kinetis, NXP's own LPC, the i.MX line). That difference is the root cause of the NXP register-extraction recall gaps we fixed, and it explains why one fix doesn't cover all NXP parts.

Why this matters

Our pipeline reads a chip's reference manual and extracts, for every hardware register, its structure — the address offset (where the register sits, relative to its peripheral's base) and the reset value (its power-on default) — and its access rules. We then diff that against the vendor's machine-readable spec (an SVD file) to catch errors. How the manual presents those facts determines how hard they are to extract. A manual that puts the offset in a clean table is easy; one that hides it in a table caption, or gives an absolute address instead of an offset, needs format-specific handling.

Two traps that break naïve extraction

  • Group B absolute addresses — the table gives 0x4004_8000, not an offset. Stored as-is it would be wrong; it must have the peripheral base subtracted.
  • Group B name cells — written Entry (ROM_ENTRY0), so the real name (ROM_ENTRY0) has to be unwrapped from the human label.
  • Group D has no table at all — the offset lives in the per-register table caption.

What our summary-fill fix covers

  • C Handled — the +8pp lpc845 win.
  • A Mostly — format is close; needs per-device validation (no verified ground truth yet).
  • B Safe no-op — needs an absolute→offset + name-unwrap adapter (covers 5 parts at once).
  • D N/A — no table; a small caption parser would be the fix if recall is weak.

STM — one family

Every STM32 reference manual states each register's location and default inline, inside that register's own subsection — not in a summary table: 

Address offset: 0x008
Reset value:    0x0000 0000

This is uniform across all 53 manuals we process. The tell: in every single one, the count of Address offset: and Reset value: labels tracks ~1:1 — meaning each register subsection declares both, in the same template, everywhere.

Even the array notation is identical old-to-new — Address offset: 0x010 + 0x004 * x, (x = 1 to 4) appears the same way in F1 and U5 manuals. There is no second STM format: summary-style tables show up only incidentally (memory-boundary maps), and the NXP caption style is essentially absent.

Why the contrast exists

It's corporate history. ST is a single company that kept one documentation template for the whole STM32 line, so one extractor generalizes across every family. "NXP" is the product of mergers — Freescale (Kinetis), NXP's own LPC line, and the i.MX series — and each legacy family carried its own manual style forward. That fragmentation is exactly why NXP extraction needed format-specific work and STM did not.

Consequences for the pipeline

  • STM needs no per-family format adapters. The inline Address offset: / Reset value: labels sit right in each register's text, so the generator reads them directly — which is why the STM pipeline scales to 53 manuals with one extractor and never needed a summary-table fill.
  • NXP needs per-group handling. The split-summary-table fix we shipped took lpc845 (Group C) address coverage from 85% → 93% (+59 offsets, +20 resets) with zero disagreements against the SVD. On Group B (classic Kinetis) it is a verified safe no-op (0 filled, 0 wrong on ke04).
  • One high-value next investment: a Group B adapter (absolute→offset + Label (NAME) unwrap) would extend the same recall win to ke04, k64, mk20d7, mk20d5 and ke04_old at once.
  • Related fix, same root cause: NXP access-rule (constraint) extraction was silently dropping everything because the quote-anchor step assumed STM file naming; after the fix, the lpc845 re-run anchored and confirmed its constraints end-to-end (0 → 3 surviving).
