# Cross-PAC generality — does the injection work beyond stm32f4?

**Date:** 2026-07-16
**Driver:** `applications/pac_codegen/experiments/cross_pac.py` (standalone;
the canonical CI crate remains stm32f4 in `test_codegen.py`).
**Fixtures:** corpus-verbatim generator output per family
(`experiments/fixtures/`, source paths in its README).

## The matrix

| PAC crate | version | svd2rust | injection | legal probe | illegal probe | tree pristine after |
| --- | --- | --- | --- | --- | --- | --- |
| stm32f1 | 0.16.0 | 0.36.1 | ok (364 register files marked) | compiles | rejected, E0277 + datasheet message | yes |

| rp2040-pac | 0.6.0 | **0.31.5** | **REFUSED (by design)** | — | — | yes |

The three STM families use real extracted constraints from their own
reference manuals (rm0008 I2C CR1 STOP/START/PEC; rm0091 I2C TIMEOUTR ⇐
TEXTEN=0 — the newer I2C IP, so F0 is not a copy of the F1 case; rm0394 SPI
CR1 ⇐ SPE). Injection, enforcement, and the diagnostic text behave
identically to stm32f4 on all three.

## The outsider crate: loud refusal, exactly as designed

rp2040-pac (the Raspberry Pi Pico's PAC, generated by svd2rust **0.31.5**,
five generations older than our 0.36.1 template) was injected with a
synthetic fixture. The injector **refused before modifying anything**, and
its diagnosis names precisely what differs: `read` and `reset` still match,
but the whole write/modify method family has different signatures in that
template generation. Nothing was half-patched; the tree digest was unchanged.

This is the boundary statement for the paper: the injector supports one
svd2rust template generation at a time (currently 0.36.x, the 0.16.0
stm32-rs wave), detects any other loudly, and the refusal output doubles as
the to-do list for a compatibility profile if one is ever wanted. Per the
2026-07-16 policy in `targets/stm.toml`, the preferred route for families
whose released HAL crates sit on older PACs is the HAL's development branch
against the newest PAC — not back-porting the injector.

## Second adoption experiment: unmodified stm32f1xx-hal 0.11.0

Same design as the stm32f4 experiment (`eval_hal/`): the released HAL crate,
consumed from crates.io, with only a `[patch.crates-io]` line swapping in the
locally injected PAC. Constraint injected: the single I2C CR1 rule.

| outcome | count | where | meaning |
| --- | --- | --- | --- |
| baseline (pristine PAC) | clean | — | adoption costs nothing |
| **true enforcement** | **20** | `i2c.rs` (11), `i2c/blocking.rs` (9) | every place the HAL writes/modifies I2C1 CR1 fails with the datasheet diagnostic — all errors name the concrete `i2c1::cr1` register |
| generic friction | 27 | `adc.rs` (18), `serial.rs` (9) | code generic over register types (associated-type registers) must re-state the marker bounds; no ADC/serial register is constrained |
| unexplained | 0 | — | — |

Classification note: friction errors carry the same "constrained by its
datasheet" message text; the distinguishing mark is whether the error names
the concrete constrained register (`i2c1::cr1::CR1rs`) or an associated-type
placeholder. The experiment runner's own summary initially binned `adc.rs`
under enforcement; the corrected attribution above is from compiler JSON
diagnostics (primary + macro-expansion spans), the same method as the
stm32f4 analysis.

Notable versus stm32f4: F1's HAL has *more* generic-over-register code (its
ADC layer), so the friction class is larger relative to enforcement — more
evidence that the paper should report the two numbers separately.

## What this licenses the paper to claim

1. Real extracted constraints from **four STM families** (F0, F1, F4, L4)
   inject and enforce identically — same-generator generality is
   demonstrated, not assumed.
2. **Two independent released HAL crates**, unmodified, fail at exactly
   their real constrained call sites (F4: 14/14 I2C; F1: 20/20 I2C) with
   zero unexplained errors.
3. Crates from **other svd2rust generations are detected and refused
   loudly** before any modification — no silent misinjection is possible.
4. Honest cost, now measured twice: trait-generic HAL code needs mechanical
   marker bounds (F4: one module; F1: two modules).
