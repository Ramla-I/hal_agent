Design review · register-access constraint grammar (v2)

What the grammar expresses, and how each kind compiles

A datasheet's rules about when and how a register may be touched are captured as a discriminated union of eight constraint kinds. From each, an enforceability class is computed, and that picks how the rule becomes Rust. This is a quick audit of the eight kinds, the ways each could be encoded, and where coverage has gaps.

02The encoding primitives — four witness-token roles

A witness token attests a past observation or action — never a present guarantee. Everything below is built from exactly four roles. The compiler enforces a rule by making the operation's type demand the right token; the token can only come into existence by doing the required thing.

03How each kind compiles — every way we could encode it

For each enforceable kind: the encoding we chose (or plan), then the alternatives. The common thread is "the operation does not type-check without evidence"; the encodings differ in what carries the evidence — a token, the register's own type, a scope, or (giving up compile-time) a runtime check.

state_gate → state witness / action witness · the one kind compiled today

A
Witness token CHOSEN
A hardware-established precondition becomes a check_*_ready() that does one fresh volatile read of the source field(s) and returns a state witness; a software-established one becomes a setup method returning an action witness. The gated write_witnessed(f, w) consumes it; the stock write gains a where REG: UnconstrainedWrite bound and the constrained register simply never implements that marker, so the witness-free path does not exist (E0277 with the datasheet message). A welded write_when_ready(f) checks and writes in one call so the token never escapes. 
// witness-free write of a gated register → compile error
i2c.mstctl.write(|w| …);              // E0277: MSTCTL is write-constrained
i2c.mstctl.write_when_ready(|w| …, &stat)?;  // checks MSTPENDING, then writes
B
Typestate — the register/peripheral carries a type parameter for the state (Usart<Disabled> vs Usart<Enabled>); the gated op exists only on the valid state, and transitions consume self. Strongest and zero-token at call sites, but invasive and per-peripheral — it rewrites the PAC's shape rather than riding the generic register proxy.
C
Newtype / sealed builder — a DisabledUsart wrapper exposes the config writes and .enable() consumes it into an EnabledUsart that lacks them. A lighter typestate; good when one disable→configure→enable arc dominates.
D
Scoped closure (RAII region) — with_disabled(|regs| { … }) establishes the precondition, runs the body, restores it. The window is the closure, so the check-to-use gap is fixed by construction; natural for "configure several registers while disabled".
E
Runtime check only — a debug_assert! or a Result-returning setter with no compile obligation. No static guarantee; this is what the gate degrades to and what a vacuous or doc-only gate is worth.

sequence → action witness · designed, not yet emitted

A
Linear token chain PLANNED — each step_n() consumes step n−1's token and mints step n's; the final step mints the enables capability. Ordering becomes a pure type-level property — the cleanest linear-types fit in the whole grammar.
B
Single transaction method — fn unlock_wpr() performs all steps internally; the individual steps are never exposed, so they can't be done out of order. Simplest, but hides the steps (no partial use).
C
Typestate progression — S0→S1→S2 types, each step a method on the previous state type.
D
Consuming builder — .step_a().step_b().commit(); same chain expressed as a fluent API.

write_once → capability · designed, not yet emitted

A
Capability consumed by value PLANNED — a non-Copy ZST minted once in the peripheral singleton; the write takes it by value, so a second write is a move-after-move error (E0382).
B
Typestate — Reg<Unwritten> → Reg<Written>; the write lives only on Unwritten and consumes self.
C
take() singleton — LOCKR.take() -> Option<WriteOnceCap> yields Some exactly once.
D
Runtime flag — a boolean guard; no compile guarantee (fallback).

clock_gate → capability (peripheral-granularity) · intentionally NOT PAC-gated — the HAL owns it

Decision (2026-10-20): we do not compile this kind. Peripheral clock enablement is already the HAL's job — options A–C below are precisely what every HAL we inject into already does (an RCC/SYSCON typestate, a Clocks token, or an enable() that hands back the peripheral), so a PAC-level clock gate would be redundant with, and weaker than, the HAL's own enforcement. clock_gate stays grammar + validation only (extracted, SVD-validated, judged, counted) and is kept out of SUPPORTED_KINDS. The encodings are listed for completeness — as the HAL-level patterns that discharge it:

A
Handle from enable PLANNED — enable_clock() returns the register-block handle; every register access needs the handle. Enforced once at the block accessor, not per register.
B
Peripheral typestate — I2C<ClockOff> → I2C<ClockOn>; the register accessors exist only on ClockOn. (This is essentially how embassy / stm32-hal already model RCC.)
C
Constructor-gated ownership — the peripheral struct is only constructible given a clock token, so holding the peripheral is the proof.

delay → state witness (ordering) + runtime duration · designed, not yet emitted

A
Token + runtime wait PLANNED — the triggering op mints a token; reaching the dependent access requires calling wait(duration), which consumes the token and returns the access capability. The ordering is compile-gated; the duration is a runtime wall-clock/cycle count and can never be compile-checked.
B
Typed delayed wrapper — a Delayed<T> that only hands out the dependent access after .wait().
C
Pure runtime — when the datasheet names no dependent access, only the duration remains, so it degrades to a bare delay(d) call (dynamic_check) with no compile gate.

value_relation → doc-only for the injector · but upholdable by combined setters at the HAL level

A relation like "CR2.FREQ must equal the APB1 MHz" or "VCO = f/(PREDIV+1)·(MULT+16), in range" is made unviolable by collapsing the related fields into one setter, so they cannot be set inconsistently.

A
Derived (combined) setter — by construction — expose one method that takes the independent input and computes the dependent field(s), hiding the individual writers (set_pll(target_mhz, src_mhz) computes valid PREDIV/MULT). The illegal combination is unrepresentable; zero runtime cost. Works when the dependent field is a pure function of inputs the API controls.
B
Typed-units / const-generic — compile-time — carry both sides as types; the relation becomes a type/const constraint. Embassy's Hertz clock tree is this: FREQ is derived from an APB1 frequency threaded through as a typed value, so the relation holds at compile time.
C
Checked combined setter — runtime — one setter takes all the related values, returns Err/asserts on violation, writes them atomically. The fallback for inequalities or relations with no computable inverse — still better than two independent writers.
D
Doc-only — when one side is an external fact the register API can't see, or the relation is too free-form to compute or check.

Why it's still doc-only for our injector: all of these are API-shape changes — a new combined method plus sealing the individual field writers (where #[private_fields]/#[nomutates] from §05 earn their keep). That is HAL/wrapper-level design, not the PAC-level gating our emitter rides on existing methods, and synthesizing the setter needs the semantic relation (and often its inverse) — which the grammar deliberately keeps as prose in datasheet_text. So a HAL author can encode it; the mechanical injector leaves it documented. Middle ground the injector CAN emit: an advisory #[deprecated(note=…)] warning on the involved field writers — document-at-use-site without owning a setter (proposed, plan §13).

read_effect · other → documentation-only

read_effect is load-bearing metadata: it tells codegen when a checking read would itself perturb state (the self-defeating same-register read-gate) and feeds the validator — it is a consequence, not an access restriction, so there is nothing to gate. other has no structure to compile and exists to measure coverage (see §04). Proposed advisory surface (plan §13): read_effect can carry a /// caveat on the register's type-alias doc (the whole-register read is generic, so it can't be per-register #[deprecated]'d — the E0592 limit) so "reading this clears RXNE" shows in rustdoc/IDE hover.

04Coverage — what's excluded, and the gaps

Deliberately not constraints (routed out at the prompt, emit nothing)

These are register facts, not access rules, and svd2rust/the SVD already carry them:

  • w1c / rc_w flag semantics (SVD modifiedWriteValues), read-to-clear standing alone (→ read_effect if worth recording)
  • access-width requirements (byte/half-word/word)
  • secure / privileged-access notes · "value is don't-care" validity notes · reset behaviour

Implementation gap (grammar expresses it, emitter doesn't yet)

Four of the eight kinds have designed encodings (§03) but are carried, not compiled — SUPPORTED_KINDS = {state_gate}. In the NXP corpus that is ~240 real constraints (sequence 152, write_once 80, delay 9) sitting enforceable-in-principle but documentation-in-practice. This is wiring, not grammar.

Candidate missing classes — grounded in the 40 other constraints we actually got

The other-rate per run is the designed coverage metric. Reading the 40 (26 confirmed) other constraints in the NXP corpus, they cluster into recognizable shapes — several deserving first-class structure rather than flattening into state_gate/value_relation or landing in other:

  • Mode-gated access (biggest cluster). "Writable only in RUN mode" (SPM_LPCTRL), "not while in VLPR" (SIM_CLKDIV1), "only in Freeze mode" (CAN RXIMR), "only in STOP/HALT" (CAU3). These are state_gates, but the precondition is a system/power mode — often not a single local field (it lives in SMC_PMSTAT etc.), so the extractor couldn't phrase it and fell to other. A cross-register state_gate with a "mode" precondition vocabulary would absorb these.
  • Write-value validity. "Only 0x00 or processor+1 are legal; other values ignored" (SEMA42 gate), "do not write 0" (WDOG_TOVAL), "reserved bits must be written 0". A restriction on the value of one field, distinct from value_relation (which relates two fields). Encodable as a typed enum of legal values or a checked setter.
  • RMW / co-write hazard. "Do not read-modify-write" (the write-only FIFOWR registers, ×5), "while writing 1 to TEN, CSR[5:1] must not be altered" (LPTMR). The hazard is the whole-word write clobbering bits you must preserve — exactly the class behind the embassy I2C OAxEN bug. Related to read_effect but framed as a write constraint; a "preserve-these-bits / modify-only" marker would capture it.
  • Buffered / shadow-register (deferred write). "The written value takes effect only on an update/load event" — timer ARR/CCR preload, PDB LDOK, FTM double-buffering. The hazard isn't when you may write but that the write is latched on event E; writing without the subsequent load silently has no effect. Encodable as an obligation or a two-phase stage()→commit() token pair.
  • Standalone obligation / postcondition. "ESFC must be set just before a flash op and cleared when it completes" (MCM_PLACR). "After X you must do Y" with no governing precondition. The obligation witness role exists but no kind mints one on its own.

(The other ~third of the other bucket is extraction noise — access-width facts like "32-bit writes only" that the prompt should have routed out to nothing. A real coverage spike would be dominated by the shapes above, not by noise.)

Net: the kind set covers the datasheet access-rule space well, and the enforceability split (two compile-gated classes by what mints the witness, plus runtime and doc-only) is principled. The real opportunities are (1) compiling the four carried kinds with the encodings in §03, and (2) giving the deferred-write and standalone-obligation hazards their own structure instead of letting them flatten into state_gate or other.

05Hardening the encodings — compiler-checked specifications

Every encoding in §03 rests on invariants that are valid Rust to break, so the compiler stays silent when a codegen regression or a hand-edit weakens a gate. Two of those invariants need no new machinery — they are already structural: the witness is unforgeable because its _priv field is private by Rust’s default visibility, and single-use because the witnessed writer takes it by value (consumes it). The rest can be pinned with static_assertions macros (assert_not_impl_any!, assert_impl_all!, assert_eq_size!, assert_eq_align!) — compile-time only, zero runtime cost — that abort compilation when a type-level property fails. The emitted next to column below says, for each, exactly where in the generated tree it attaches, and flags the rows with no application in this (svd2rust) PAC. Proposed: the emitter would drop the applicable macros beside each gate it generates.

Concretely, where they attach in the code the emitter already generates:

// in the injected `constraints` module (appended to the mstctl peripheral file),
// beside each gate — these are the real static_assertions macros the emitter would drop:
assert_not_impl_any!(super::mstctl::MSTCTL_SPEC: crate::UnconstrainedWrite); // the gate is still a gate
assert_impl_all!(super::mstctl::MSTCTL_SPEC: crate::WriteGate);              // …and still carries the witnessed path
assert_not_impl_any!(MstctlWriteWitness: Clone, Copy, Default, Send, Sync);  // can’t be duplicated, forged, or escape to an ISR
assert_eq_size!(MstctlWriteWitness, ());                                     // …and is zero-sized

// NO attribute is emitted for unforgeability or single-use — both are already structural:
pub struct MstctlWriteWitness { _priv: () }  // private field ⇒ unforgeable   (no #[private_fields])
pub fn write_witnessed<F>(&self, f: F, _witness: <REG as WriteGate>::Witness) { … }  // by-value ⇒ consumed (no #[consumes])
The two that matter most

assert_not_impl_any!(SPEC: UnconstrainedWrite) defends the thing our scheme is — a gate expressed as an absence, which is invisible to re-introduce — and its positive twin assert_impl_all!(SPEC: WriteGate) pins that the gated register still has its witnessed path. The freshness/affine property needs no spec: the witness is a by-value parameter, so “the token is spent” is already enforced by the signature itself.

The assertions fall into two intents: most defend each gate against weakening (unforgeability, gate-presence, affine use, ZST-ness); the last — assert_eq_size!/assert_eq_align! on the RegisterBlock — defends the injection itself, guaranteeing the gated PAC is byte-for-byte ABI-identical to the pristine one so no register offset ever moves. Both are generated right beside the code they protect, so a weakened gate or a shifted layout fails to compile instead of shipping.

What it does not reach: these harden the plumbing (unforgeability, gate-presence, affine use, layout), not the semantics. No spec can verify that check_write_ready() performs a real fresh read — a stub that returns Ok(witness) passes every assertion. CCS defends the encoding against regression; it does not extend what the grammar can express.

06The svd2rust interface as substrate — the levers it gives, the walls it imposes

Every encoding in §03, every hardening spec in §05, and every doc-only/advisory fallback traces back to a small set of things the svd2rust-generated PAC lets us do — and a handful it forbids. The forks in building the emitters were really the process of mapping those walls. The gate is never grafted onto the PAC; it rides what svd2rust already is. So the enforcement ceiling isn't the grammar — it's the interface.

The levers — everything above is built from these

  • Trait-bound method availability — svd2rust already gates write on where REG: Writable; we add where REG: Unconstrained{Write,Modify,Read} and withhold the marker on constrained registers. Absence of a marker is the gate. This is THE primitive — state_gate, write_once, and sequence all ride it.
  • Affine move (consume-by-value) — a non-Copy witness/capability taken by value can't be reused (E0382) → single-use and write-once.
  • #[must_use] — a token that warns when dropped unused → obligations ("you still owe a step") and the proposed obligation kind.
  • The register's type-alias doc — pub type FOO = Reg<FOOrs> is ours to annotate with /// → the advisory channel when nothing active is possible.
  • #[diagnostic::on_unimplemented] on the marker trait → turns the bare E0277 into the datasheet sentence at the call site.

The pattern

Each kind's ceiling is set by which wall it meets. state_gate / write_once / magic-value sequence reach the trait-bound lever cleanly and compile-enforce. value_relation / read_effect / data-port sequence steps hit the generic-method wall and fall to the doc/advisory lever. delay / clock_gate hit the no-timing wall and become HAL-owned. The grammar can express more than svd2rust can enforce — which is exactly what the other bucket and the doc-only tier are for.
