# Injecting constraints into embassy and Tock — feasibility report

**Question.** What would it take to inject our register-access constraints into
the *embassy* and *Tock* frameworks (so their own firmware compiles against gated
registers), rather than only reaching them incidentally through a shared
stm32-rs PAC? **Report only — no code changes.**

## How our injection works today (the assumption it rests on)

The enforcement arm patches an **svd2rust**-generated PAC. For each gated
register it (a) omits the `Unconstrained{Read,Write,Modify}` marker-trait `impl`
on that register's *spec type* (svd2rust generates one type per register, e.g.
`usart1::cr1::CR1rs`), and (b) attaches a `#[diagnostic::on_unimplemented]`
message. The register's `.read()/.write()/.modify()` methods carry a witness
bound; **absence of the marker = the access won't type-check** without a witness.
The emitter (`applications/pac_codegen/rust_codegen.py`) is svd2rust-shaped:
one-spec-type-per-register, the `Reg<REG>` wrapper, the `Readable/Writable`
traits.

Neither embassy nor Tock uses svd2rust. That's the whole problem.

## embassy → `stm32-metapac`

**Register model (verified, stm32-metapac 21.0.0).** embassy-stm32 accesses
hardware through **`stm32-metapac`**, generated by *chiptool* from the
*stm32-data* database — not svd2rust. Its core (`common.rs`) is:

```rust
pub struct Reg<T: Copy, A: Access> { ... }          // T = value type, A = R/W/RW
impl<T: Copy, A: Read>  Reg<T, A> { pub fn read(&self) -> T { ... } }
impl<T: Copy, A: Write> Reg<T, A> { pub fn write_value(&self, v: T) { ... }
                                    pub fn write<R>(&self, f: ...) -> R { ... } }
impl<T: Copy, A: Read + Write> Reg<T, A> { pub fn modify<R>(&self, f: ...) -> R { ... } }
```

Access is **already trait-bounded** (`read` needs `A: Read`, `write` needs
`A: Write`). That is a *cleaner* insertion point than svd2rust — the machinery
for "gate an operation behind a trait bound" is present.

**What it would take:**
1. **A metapac-shaped emitter.** Add a witness bound to `write`/`write_value`/
   `modify` (and `read` for read-effects) keyed on the **value type `T`**
   (e.g. `where T: UnconstrainedWrite`), then generate `impl UnconstrainedWrite
   for regs::Cr1 {}` for every *non-gated* register (absence = gate), and a
   `#[diagnostic::on_unimplemented]`. This is our svd2rust scheme re-pointed from
   the register spec type to metapac's value type `T`. A new emitter alongside
   `rust_codegen.py`; the gating idea transfers, the code shape does not.
2. **A name/identity map.** Our constraints are keyed on SVD/svd2rust names;
   metapac names differ (`usart_v1::Cr1`, peripheral *versions* not instances).
   Need SVD-name → metapac-name mapping per manual/device.
3. **Shared-value-type attribution.** metapac shares one value type per
   *peripheral version* — `usart_v1` and `usart_v2` both expose `cr1() -> Reg<regs::Cr1, RW>`,
   and all v1 USART instances share `regs::Cr1`. So gating `regs::Cr1` gates
   **every v1 USART at once** — the same union/projection attribution problem we
   already hit (a hit says "some v1 USART", not "USART3"). Field-level gating
   would sit on the value type's field setters.
4. **Generated-source patching.** metapac is generated, so patch the emitted
   crate (like we patch svd2rust output) or teach chiptool the markers.

**Feasibility: MEDIUM.** The trait-bound access model helps; the real costs are a
second emitter, the name map, and per-version attribution. embassy is also
heavily async/generic, so — exactly like stm32-hrtim — most accesses only
monomorphise in **real firmware** (a ceiling), and generic projections attribute
weakly.

**Payoff: HIGH.** Today embassy is reachable *only* through its optional
`stm32-hrtim` path (its core peripherals go through metapac, which we don't
touch). Injecting metapac makes embassy's **core** peripherals gateable — a very
large, active firmware population becomes real blast radius, and embassy firmware
could be measured for genuine bugs, not just the hrtim corner.

## Tock → `tock-registers` (hand-written, no PAC)

**Register model.** Tock defines registers with the **`tock-registers`**
`register_structs!` macro: `ReadWrite<u32, REG::Register>` fields with bitmask
field markers (`CR1::PE::SET`). These maps are **hand-written per chip**
(`chips/stm32f4xx`, `chips/stm32f303xc` are the only STM32 ones), generated from
nothing. `scan_projects.py` already records Tock as *"tock-registers, not
svd2rust… has no PAC at all, so it can never be built against one"* — it is
**scan-only by construction** today.

**What it would take:**
1. **Gate `tock-registers`' `ReadWrite`.** Add a witness bound to `write`/
   `modify` keyed on the register marker `R` (the `REG::Register` type param),
   `impl`'d for non-gated registers — or wrap gated registers in a gated newtype.
   But `ReadWrite` is a shared upstream library type, so this changes
   *everything* unless done carefully (absence = gate would gate the entire
   ecosystem).
2. **Annotate hand-written chip maps.** There is **no generator to target** —
   the register structs are hand-authored, so injection is a *source-transform
   pass* over each chip's `register_structs!` (or manual annotation) to mark
   which registers are gated. Per chip, per register.
3. **Name map with no SVD.** Identity comes from the hand-written `REG::Register`
   / `REG::FIELD` names, which need mapping to our constraint names per chip and
   may not match the SVD spelling.

**Feasibility: LOW / HARD.** No generated artifact to patch, a shared upstream
register type, and per-chip hand-written maps make this an invasive
re-architecture. Tock's STM32 coverage is also thin (two chips).

**Payoff: LOW–MEDIUM.** Tock is *already covered* by the source scan (the
`_TOCK_ACCESS`/`_TOCK_FIELD` regexes find the same `.modify(CR1::PE::SET)`
accesses). Compile-time gating would add type-level guarantees but buys little
over the existing scan for a framework that can't be built against a PAC anyway.

## Comparison

| | svd2rust PAC (today) | embassy / stm32-metapac | Tock / tock-registers |
|---|---|---|---|
| Register source | generated (svd2rust) | generated (chiptool/stm32-data) | **hand-written per chip** |
| Access gating hook | marker traits on spec type | **trait-bounded `Reg<T,A>`** (clean) | `ReadWrite<u32,R>` (shared lib type) |
| Gate key | one type per register | value type `T`, shared **per version** | register marker `R`, per chip |
| New emitter needed | — | yes (metapac-shaped) | no emitter — source transform |
| Name map | native | SVD→metapac (per-version) | SVD→hand-written names |
| Attribution | mostly concrete | union per peripheral-version | per hand-written marker |
| Feasibility | (done) | **medium** | **low/hard** |
| Payoff | — | **high** (core embassy population) | low (already scanned) |

## Recommendation

- **embassy is the worthwhile target.** metapac's `Reg<T, A>` trait-bounded
  access is a natural place to attach a witness bound; the effort is a
  metapac-shaped emitter + an SVD→metapac name map + handling per-version shared
  value types. That unlocks embassy's *core* peripherals — the large firmware
  base we currently miss.
- **Leave Tock scan-only.** No generated artifact, a shared upstream register
  type, and hand-written per-chip maps make compile-time injection a poor
  trade against the source scan that already covers it.
- **Shared prerequisite for both:** a name/identity map from our SVD-keyed
  constraints to the framework's register/field naming, plus the same
  generic-monomorphisation caveat we saw with stm32-hrtim (real bugs surface
  only when firmware instantiates the generic accessors — a ceiling, measured by
  building actual firmware, not a bare probe).
