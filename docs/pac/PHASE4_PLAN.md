# Phase 4: Integrating Constraint Support into svd2rust

## Goal

Modify svd2rust itself so that the PAC crate changes currently applied by `rust_codegen.py` (Phase 3) are generated automatically during normal `svd2rust` code generation. This eliminates the post-processing step and makes constraint-aware PAC generation a first-class feature.

## Current State (Phase 3 — External Post-Processing)

Today, generating a constrained PAC requires:

1. Run `svd2rust` normally to produce the PAC crate
2. Run `rust_codegen.py --inject` which:
   - Patches `generic.rs`: widens field visibility, adds `ConstrainedReg<REG>` struct
   - Patches `mod.rs`: injects `pub mod constraints { ... }` into the peripheral module
   - Patches `mod.rs`: rewrites `pub type CR1 = crate::Reg<...>` → `crate::ConstrainedReg<...>`

This works but has drawbacks:
- Fragile regex-based patching of generated code
- Must re-run after every `svd2rust` regeneration
- Constraint definitions live in a separate JSON file, disconnected from the SVD/build pipeline
- No upstream path — every user must maintain the post-processing script

## Constraint Input Format

### Where Constraints Come From

Constraints are hardware preconditions extracted from datasheets — e.g., "STOP, START, and PEC bits must be cleared before writing to I2C CR1." The SVD format has no native field for these. We need an external specification.

### Proposed: `constraints.toml` Alongside `svd2rust.toml`

A new TOML file (default path: `constraints.toml`, overridable via `--constraints` CLI flag or `constraints_file` in `svd2rust.toml`):

```toml
# constraints.toml — Hardware access constraints for svd2rust

[[register]]
peripheral = "I2C1"
register = "CR1"

[[register.constraint]]
target_operation = "write"
datasheet_text = "Software should not write to CR1 while STOP=1, START=1, or PEC=1"

[[register.constraint.precondition]]
field = "STOP"
required_state = "cleared"

[[register.constraint.precondition]]
field = "START"
required_state = "cleared"

[[register.constraint.precondition]]
field = "PEC"
required_state = "cleared"
```

The `required_state` values are:
- `"cleared"` — bit must be 0 (maps to `bit_is_clear()`)
- `"set"` — bit must be 1 (maps to `bit_is_set()`)
- `"equals:<N>"` — multi-bit field must equal N (maps to `bits() == N`)

### Why TOML, Not SVD Extensions

- SVD is a CMSIS standard; adding custom elements requires vendor extensions (`<xs:any>`) that are poorly supported
- TOML is already used by svd2rust for configuration (`svd2rust.toml`)
- Constraints can be maintained independently of SVD files (which are often vendor-provided and not editable)
- Could later be auto-generated by the hal_agent pipeline and fed directly into svd2rust

## svd2rust Integration Points

### Overview of Changes

```
svd2rust source tree:
  src/
    config.rs                    ← Add ConstraintConfig, parse constraints.toml
    main.rs                      ← Add --constraints CLI flag, load constraints
    lib.rs                       ← Thread constraints through to generate()
    generate/
      generic_reg_vcell.rs       ← Add ConstrainedReg struct (static template)
      register.rs                ← Conditionally emit ConstrainedReg type alias
      constraint.rs              ← NEW: Generate constraint modules (tokens, verify, write_constrained)
      peripheral.rs              ← Inject constraint module after register module
      mod.rs                     ← Declare constraint module
```

### 3. Static Template: `ConstrainedReg` (`generic_reg_vcell.rs`)

Append to the existing static template file. This code is always included (it's inert if never referenced):

```rust
/// A register wrapper indicating hardware write constraints exist.
/// Forwards all operations via Deref to Reg; constraint modules add
/// write()/modify() shadows as inherent methods.
#[repr(transparent)]
pub struct ConstrainedReg<REG: RegisterSpec> {
    pub(crate) reg: Reg<REG>,
    _marker: marker::PhantomData<REG>,
}

unsafe impl<REG: RegisterSpec> Send for ConstrainedReg<REG> where REG::Ux: Send {}

impl<REG: RegisterSpec> core::ops::Deref for ConstrainedReg<REG> {
    type Target = Reg<REG>;
    #[inline(always)]
    fn deref(&self) -> &Reg<REG> {
        &self.reg
    }
}
```

**Field visibility changes** to the existing template:
- `Reg.register`: change from `register: vcell::VolatileCell<REG::Ux>` to `pub(crate) register: vcell::VolatileCell<REG::Ux>`
- In `generic.rs`: change `raw::R._reg` from `pub(super)` to `pub(crate)`
- In `generic.rs`: change `raw::W._reg` from `pub(super)` to `pub(crate)`

These visibility changes are harmless for PACs without constraints (still crate-private).

**Debug impl**: Conditionally generated in `register.rs` when `impl_debug` is enabled and the register has constraints (since `RegisterBlock` derives `Debug`). Alternatively, always include in the template:

```rust
impl<REG: Readable> core::fmt::Debug for ConstrainedReg<REG>
where
    R<REG>: core::fmt::Debug,
{
    fn fmt(&self, f: &mut core::fmt::Formatter<'_>) -> core::fmt::Result {
        core::fmt::Debug::fmt(&**self, f)
    }
}
```

### 5. Constraint Module Generation (`generate/constraint.rs` — NEW)

A new module that generates the constraint `TokenStream` for a given register. This is the Rust equivalent of `generate_constraint_module()` in `rust_codegen.py`, but using `proc_macro2`/`quote` instead of string building.

```rust
use proc_macro2::{Ident, Span, TokenStream};
use quote::quote;
use crate::config::{Constraint, Precondition, RegisterConstraint};

pub fn render(
    reg_constraint: &RegisterConstraint,
    regspec_ty: &Ident,
    reg_mod: &Ident,
    config: &Config,
) -> TokenStream {
    let mut out = TokenStream::new();

    // Collect all unique preconditions
    let all_preconditions = collect_preconditions(reg_constraint);

    // Generate witness token structs
    for pre in &all_preconditions {
        let token_ty = token_ident(&pre.field, &pre.required_state);
        let doc = format!("Proof that {} is {} in the register.", pre.field, pre.required_state);
        out.extend(quote! {
            #[doc = #doc]
            pub struct #token_ty(());
        });
    }

    // Generate ConstraintError enum
    let variants: Vec<_> = all_preconditions.iter().map(|pre| {
        error_variant_ident(&pre.field, &pre.required_state)
    }).collect();
    out.extend(quote! {
        #[derive(Debug, Clone, Copy, PartialEq, Eq)]
        pub enum ConstraintError {
            #(#variants,)*
        }
    });

    // Generate verify methods on R
    // ... (impl super::{reg_mod}::R { verify_*() })

    // Generate write_constrained, modify_constrained, write, modify
    // on impl crate::ConstrainedReg<super::{reg_mod}::{regspec_ty}>
    for constraint in &reg_constraint.constraint {
        // ... token params, write_constrained body, modify_constrained body,
        //     write shadow, modify shadow
    }

    out
}
```

Key functions:
- `token_ident(field, state)` → `Ident` for e.g. `StopClearedToken`
- `error_variant_ident(field, state)` → `Ident` for e.g. `StopNotCleared`
- `state_to_check(field, state)` → `TokenStream` for e.g. `r.stop().bit_is_clear()`
- `render_write_constrained(...)` → `TokenStream` for the safe write method body
- `render_modify_constrained(...)` → `TokenStream` for the safe read-modify-write body
- `render_write_shadow(...)` → `TokenStream` for the `write()` shadow that requires tokens
- `render_modify_shadow(...)` → `TokenStream` for the `modify()` shadow that requires tokens

### 6. Constraint Module Injection (`peripheral.rs`)

In `peripheral.rs`, after `register::render()` is called for each register, check if constraints exist and append the constraint module:

```rust
// Inside the register rendering loop:
let reg_tokens = register::render(register, path, dpath, &index, config)?;
mod_items.extend(reg_tokens);

// Check for constraints on this register in this peripheral
if let Some(reg_constraint) = config.constraints.get(peripheral_name, register_name) {
    let constraint_mod = constraint::render(reg_constraint, &regspec_ty, &mod_ty, config);
    mod_items.extend(quote! {
        pub mod constraints {
            #constraint_mod
        }
    });
}
```

The constraint module must be emitted inside the peripheral module, as a sibling to the register module — matching the current `pub mod constraints` placement.

## Future Extensions

### Auto-Generation from hal_agent

The hal_agent pipeline (s1a → s4 → s5) extracts register constraints from datasheets and validates them. A natural extension is to emit `constraints.toml` directly from the pipeline's validated output, closing the loop:

```
Datasheet → hal_agent → constraints.toml → svd2rust → Constrained PAC → HAL
```

### Multiple Registers

The current implementation constrains I2C1 CR1 as a proof of concept. The architecture already supports multiple registers — `constraints.toml` simply has multiple `[[register]]` entries. Each gets its own `pub mod constraints` block and `ConstrainedReg` type alias.

### Shared Constraints Across Peripheral Instances

I2C2, I2C3 etc. share the same register layout as I2C1 via `derivedFrom` in the SVD. svd2rust generates `pub use i2c1 as i2c2`. The `ConstrainedReg` type alias and constraint module would be inherited automatically through the re-export — no per-instance duplication needed.

### Field-Level Constraint Granularity

#### The Problem

Currently, a constraint on *any* field in a register promotes the *entire* register to `ConstrainedReg`, which means `write()`/`modify()` require tokens even when the caller only touches unconstrained fields. For a register-level constraint like I2C CR1 ("do not write while STOP/START/PEC are set"), this is correct — `modify()` performs a full register write regardless of which fields the closure touches, so the hardware sees all bits being written.

But consider a hypothetical constraint: "field X must be 0 before writing field Y." A `modify()` that only changes field Z (leaving Y untouched) would still demand tokens, which is unnecessarily restrictive. The key question is whether the constraint is about the **register write operation** or about **specific field values being written**.

#### Why This Is Hard

`modify(|r, w| ...)` is a single atomic read-modify-write. At the Rust type level, the `W` struct exposes all fields — there's no way to know at compile time which fields the closure will actually modify. The closure receives `&mut W<CR1rs>` and can call any field writer on it.

#### Possible Approaches

**Approach A: Split Writer Types (most promising)**

Generate two writer types per constrained register — one exposing only unconstrained fields, one exposing all fields:

```rust
// Unconstrained writer — only exposes PE, ACK, ENGC, etc.
pub type W_Free = crate::W_Free<cr1::CR1rs>;

// Full writer — exposes all fields including STOP, START, PEC
pub type W = crate::W<cr1::CR1rs>;
```

With corresponding methods:

```rust
impl ConstrainedReg<CR1rs> {
    // Free path — no tokens needed, but can only touch safe fields
    pub fn modify_free<F>(&self, f: F)
    where
        F: FnOnce(&R<CR1rs>, &mut W_Free<CR1rs>) -> &mut W_Free<CR1rs>;

    // Constrained path — tokens required, all fields accessible
    pub fn modify<F>(&self, f: F, tokens...)
    where
        F: FnOnce(&R<CR1rs>, &mut W<CR1rs>) -> &mut W<CR1rs>;
}
```

**Tradeoff**: This requires generating a parallel writer type that omits constrained field accessors. The `W_Free` struct would need to be a newtype around `W` that only exposes a subset of field writers. This is ~50-80 additional lines of generated code per constrained register and adds complexity to the field generation in `register.rs`.

**Approach B: Field-Writer-Level Tokens**

Require tokens at the field writer level rather than the register write level:

```rust
i2c1.cr1().modify(|_, w| {
    w.pe().set_bit();                              // free — no token
    w.stop().set_bit_with(stop_cleared_token);     // needs token
});
```

**Tradeoff**: This changes the svd2rust field writer API (`BitWriter`, `FieldWriter`) for constrained fields, which is a much deeper change. Field writers are generic types shared across all registers — adding per-field token parameters would require specialization or a parallel set of writer types. The chaining API (`w.field1().set_bit().field2().clear_bit()`) would also break since token consumption is a move.

**Approach C: Runtime Field Mask Checking**

Keep compile-time tokens for the register write, but add a runtime check that verifies which fields were actually modified:

```rust
// modify_partial reads the register, lets closure modify W, then compares
// old vs new bits to determine which fields changed. If only unconstrained
// fields changed, no tokens are needed.
pub fn modify_partial<F>(&self, f: F)  // no tokens
```

**Tradeoff**: Moves constraint enforcement from compile time to runtime, which defeats the purpose of the witness token approach. Also, the "which fields changed" check has overhead and edge cases (what if the closure writes the same value back?).

#### Recommendation

For Phase 4, keep the current register-level granularity. It's correct for the majority of real-world constraints (which tend to be register-level write preconditions). Document the limitation clearly.

If field-level granularity becomes necessary for specific registers, **Approach A (split writer types)** is the most promising: it preserves compile-time safety, doesn't change the core svd2rust writer infrastructure, and the cost is localized to registers that opt in. It could be added as a `granularity = "field"` option in `constraints.toml`:

```toml
[[register]]
peripheral = "SOME_PERIPH"
register = "SOME_REG"
granularity = "field"  # default: "register"

[[register.constraint]]
target_operation = "write"
target_fields = ["FIELD_Y"]  # only these fields require tokens
# ...
```

### Upstream Contribution

The long-term goal is to propose this as an svd2rust feature via an RFC to the [rust-embedded](https://github.com/rust-embedded/svd2rust) project. The modular design (optional `constraints.toml`, inert `ConstrainedReg` struct, no changes to unconstrained registers) minimizes risk and makes the feature opt-in.
